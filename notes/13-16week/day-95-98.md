Day 96：Jinja2 模板 + ce_config 下发

templates/loopback.j2：

interface LoopBack100
 description {{ loopback_desc }}

手册任务（平铺 lines，第一次能通，接口已存在后再跑会踩坑，见下文）：

Day 97：幂等性

同一个 playbook 连跑两次，第二次 changed=0。好的自动化是重复执行安全的——已经是目标状态就什么都不做。Netmiko send_config_set 每次无脑重发，差距在 状态比对。

vars_demo.yaml：

- name: 变量驱动——先看将要下发什么
  hosts: huawei
  gather_facts: false
  tasks:
    - name: 打印本机参数
      ansible.builtin.debug:
        msg: "{{ inventory_hostname }} LoopBack100 {{ loopback_ip }} {{ loopback_desc }}"
playbook.yaml（必须有 hosts + tasks，模块不能顶格）：

- name: 用模板下发 LoopBack100
  hosts: huawei
  gather_facts: false
  tasks:
    - name: 用模板下发 Loopback 配置
      community.network.ce_config:
        parents: interface LoopBack100
        lines:
          - description {{ loopback_desc }}
          - ip address {{ loopback_ip }} 255.255.255.255
不要加 save: true（一保存往往标 changed，幂等演示会被搅浑）。

2.验收
(1)`host_vars/R1.yml` 里的变量在哪一层优先级？
答:主机级，高于 group_vars、低于 playbook vars 和 -e

(2)`lookup('template', ...)` 干了什么？
答:用当前主机变量渲染 Jinja2 模板，返回渲染后的文本——"模板+数据=配置"的 Ansible 原生形态

(3)什么是幂等性？为什么它是配置管理的生命线？
答:重复执行同一操作，结果和只执行一次一样；配置管理要频繁重跑收敛状态，不幂等的脚本每跑一次就多一分事故风险

(4)你的 Netmiko 下发脚本为什么不具备幂等性？
答:它无状态下发：不知道设备当前是什么样，每次都全量重发；没有"现状 vs 目标"的比对环节

(5)`ce_config` 下发配置后，设备配置保存（save）了吗？
答:没有——和 Netmiko 一样，保存要单独显式执行（ce_config 有 save_when 参数可配，但默认行为要心里有数）
