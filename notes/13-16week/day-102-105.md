## Day 102：动态 inventory 概念
### 静态清单的痛点
当前 lab 使用 `~/code/ansible-lab/hosts.ini`：
```ini'''
[huawei]
R1 ansible_host=192.168.30.252
R2 ansible_host=192.168.30.253
设备增减、改 IP 都要 手工改文件。若 CMDB 里已更新而 hosts.ini 未改，就会出现 第二份真相，巡检/备份连错对象。

动态 inventory 是什么
清单不由人手维护，而由脚本或插件在运行时从数据源生成（云平台 API、CMDB、数据库、Excel 导出等）。Ansible 拿到的仍是标准的 inventory JSON（主机、组、变量），后面 playbook / role 不用改。

一句话：清单即数据；数据应有单一事实来源（CMDB），不该有第二份手工拷贝。

本地可做的练习（无需云账号）
在 ansible-lab 里查看 Ansible 合并后 的主机视图（静态 + group_vars + host_vars + vault）：

cd ~/code/ansible-lab
ansible-inventory --list --ask-vault-pass
ansible-inventory --host R1 --ask-vault-pass
理解：hosts.ini 只是数据源之一；动态 inventory 只是 换了一种生成同样结构的方式。

Day 103：AWX 认知（只建立认知，不安装）
AWX 是什么
AWX = Ansible 的 开源 Web 管理面（Red Hat Ansible Automation Platform 的上游）。底层仍是 Ansible 引擎；变的是 谁触发、何时跑、凭据怎么管、结果怎么留痕。

本机命令行	AWX / 自动化平台
ansible-playbook site.yml --ask-vault-pass
浏览器发起 Job、定时任务
每人自己输 vault/SSH 密码
Credential 凭据库集中管理
日志在终端
任务历史、审计、RBAC 权限
脚本各自 cron
统一调度与 API（CI/工单对接）
和当前 lab 的关系
site.yml、roles/device_backup、loopback_config 剧本不变。
AWX 负责：在控制节点上 按 schedule 跑同一套 playbook、把 vault 密码存凭据库、给网工/Web 界面点「备份」。
为什么现在不装
现代 AWX 依赖 Kubernetes。阶段 4 尚未系统学容器/K8s 时安装 = 先啃编排再学自动化，顺序颠倒。手册要求：只认知，不安装；等公司环境已有 AWX 或学完 K8s 再回来。

2.验收
(1)动态 inventory 解决什么痛点？
答:静态清单与真实环境脱节——设备增减靠人记；动态 inventory 实时从云平台/CMDB 拉清单，永远和现网一致

(2)"清单即数据，单一事实来源"怎么理解？
答:设备信息应该只有一份权威来源（CMDB/云平台），inventory 是它的投影；手工维护第二份拷贝必然腐化漂移

(3)AWX 是什么？为什么现在不学安装？
答:Ansible 的开源 Web 管理面（定时/权限/API/可视化）；现代 AWX 依赖 K8s 部署，容器没学前装它是事倍功半——先记生态位

(4)Ansible 的两个强项一个弱项？
答:强项：声明式+幂等、无 agent 零被管端依赖；弱项：复杂逻辑写起来笨拙、报错链路长（任你答出合理版本即可）

(5)网络自动化里 Ansible 和 Python 脚本怎么分工（你的当前答案）？
答:状态收敛/批量配置管理用Ansible；复杂解析、定制逻辑、数据处理用Python--两者通过"Ansible调自定义模块/API"衔接
