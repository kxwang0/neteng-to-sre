Day 38：send_config_set——第一次用代码改设备配置

from netmiko import ConnectHandler
from getpass import getpass

conn = ConnectHandler(device_type="huawei", host="192.168.x.x",
                      username="netops", password=getpass("输入设备密码: "))

# 下发一个无害的 Loopback 练手
cmds = [
    "interface LoopBack 100",
    "description configured-by-python",
    "ip address 10.255.0.1 255.255.255.255",
]
print(conn.send_config_set(cmds))

# 验证
print(conn.send_command("display interface LoopBack 100"))
conn.disconnect()

然后练回退（好习惯从第一天养）：

conn.send_config_set(["undo interface LoopBack 100"])

三条纪律（以后写配置类脚本的铁律）：
只在模拟器练手，生产设备的配置下发要过评审
send_config_set 会自动进/出配置视图，但 save 要单独发（conn.send_command("save", expect_string="Y") 类写法，或设备上先配好自动保存）
每次下发后必须跟一条验证命令，确认配置真生效了

Day 39：异常细化——让失败有意义
import logging
from netmiko import ConnectHandler
from netmiko.exceptions import NetmikoTimeoutException, NetmikoAuthenticationException

try:
    conn = ConnectHandler(**dev)
except NetmikoTimeoutException:
    logging.error("%s 连接超时：网络不通或设备没开 SSH", dev["host"])
except NetmikoAuthenticationException:
    logging.error("%s 认证失败：用户名/密码或 aaa 配置问题", dev["host"])
except Exception as e:
    logging.error("%s 未预期错误：%s", dev["host"], e)

注意顺序：具体的异常在前，兜底的 Exception 在后——反过来的话具体异常永远轮不到，精确处理就失效了。故意把 IP 改错、密码改错各跑一次，看日志是否说出了"人话"。

Day 40：并发采集——10 台设备和 1 台一样快
from concurrent.futures import ThreadPoolExecutor, as_completed
from netmiko import ConnectHandler

def collect(dev):
    conn = ConnectHandler(**dev)
    output = conn.send_command("display version")
    conn.disconnect()
    return dev["host"], output

devices = [
    {"device_type": "huawei", "host": "192.168.x.11", "username": "netops", "password": "..."},
    {"device_type": "huawei", "host": "192.168.x.12", "username": "netops", "password": "..."},
    {"device_type": "linux",  "host": "192.168.x.A",  "username": "kxwang", "password": "..."},  # Rocky 本机凑数
]

with ThreadPoolExecutor(max_workers=5) as pool:
    futures = {pool.submit(collect, d): d for d in devices}
    for fut in as_completed(futures):
        host, output = fut.result()
        print(f"{host} 采集完成，{len(output)} 字节")


原理：采集的时间花在等设备回包（I/O 等待），不是在算数。一个线程等回包时，其他线程在干活——所以 I/O 型任务用线程池立竿见影
max_workers=5 别贪大：每条连接占设备一个 VTY 会话（华为默认 0–4 共 5 个），开太多设备直接拒绝登录
没那么多设备？EVE 里把 R1 克隆两台（改不同 IP），或像上面一样拿 Rocky 本机（device_type="linux"）凑数——重点是练并发结构

2.验收
(1)send_command 和 send_config_set 的区别？config_set 自动化了什么？
答:command 发查看命令拿返回；config_set 自动进入配置视图、逐条下发、退出视图——但不替你 save，保存要单独发

(2)配置下发类脚本的三条安全纪律？
答:只在模拟器验证 → 单台灰度 → 才批量；每次下发后跟验证命令；提前写好回退命令

(3)为什么采集类任务用多线程就有效，不需要上多进程？
答:瓶颈在 I/O 等待（等设备回包）不在计算；线程等回包时让出执行权，并发就有收益。计算密集型任务才需要多进程（Python 的 GIL 限制了多线程的并行计算能力，但不限制 I/O 并发）

(4)max_workers 为什么不能开 100？
答:每条连接占设备一个 VTY 会话，默认就 5 个；且大量并发对设备 CPU 不友好。5–10 是合理区间

(5)except 块为什么具体异常必须写在 Exception 前面？
答:except 从上往下匹配，大网（Exception）放前面会把具体异常全部截胡，后面的精确处理永远执行不到
