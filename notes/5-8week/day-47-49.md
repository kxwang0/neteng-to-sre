### Day 47–49 详细手册：Git 进阶——分支、冲突与 PR 流程（每天约 2 小时）

> 上周你改错 commit message 已经摸过 rebase 了。这周把 Git 从"个人备份工具"升级成"协作工具"——这是 DevOps 团队的日常。

**Day 47：分支基础**

```bash
cd ~/code/neteng-to-sre
git switch -c feature/backup-v2      # 新建并切换分支（等价 git checkout -b）
# ... 在分支上改代码、提交 ...
git switch main                       # 切回主分支
git merge feature/backup-v2           # 把分支成果合回来
git branch -d feature/backup-v2       # 删掉已合并的分支
```

网工类比：分支 = 配置实验台（candidate configuration），随便改不影响现网；merge = commit 合入运行配置；`branch -d` = 实验台用完拆掉。

**Day 48：故意制造一次冲突并解决它**（冲突只有亲手解一次才会）

```bash
git switch -c test/conflict-a
# 改 README.md 第一行为 "版本 A"，commit
git switch main
# 改 README.md 同一行为 "版本 B"，commit
git merge test/conflict-a             # 砰，冲突
```

打开冲突文件会看到三块标记：

```javascript
<<<<<<< HEAD
版本 B          ← 当前分支的内容
=======
版本 A          ← 要合进来的分支的内容
>>>>>>> test/conflict-a
```

手工改成你想要的样子（删掉三行标记），然后 `git add README.md && git commit`——冲突解决完毕。

**Day 49：给自己提一个 PR**

```bash
git switch -c feature/readme-update
# 改点东西，commit
git push -u origin feature/readme-update    # 分支推上 GitHub（先 gtest）
```

然后到 GitHub 网页：仓库页会出现 `Compare & pull request` 按钮 → 点进去写说明 → `Create pull request` → 自己当 reviewer 看一遍 diff → `Merge pull request` → 删分支。本地 `git switch main && git pull` 同步回来。

为什么 solo 也要走 PR：**这是给面试官看的流程痕迹**，也是肌肉记忆——上班第一天就要天天提 PR。

`rebase` 补一句认知：merge 保留真实历史（多一条合并 commit），rebase 把提交"搬"成一条直线（历史干净但哈希全变）。**公共分支绝不 rebase**，自己的本地分支随便用（你上周改 commit message 用的 `rebase -i` 就是它的交互模式）。

2.验收
(1)分支解决了什么问题？为什么不直接在 main 上改？
答:把未完成的工作隔离：main 随时保持"可用的稳定版"，实验在分支上随便造，成了再合回来；直接改 main 等于在现网设备上直接配

(2)冲突的三块标记各是什么含义？
答:`<<<<<<<` 到 `=======` 是当前分支（HEAD）的内容；`=======` 到 `>>>>>>>` 是合入分支的内容；三块标记都要删掉，留下你要的最终内容

(3)`git switch -c` 和 `git switch` 的区别？
答:带 `-c` 是新建分支并切换；不带是切换到已有分支

(4)PR 流程比直接 push 多了什么？团队为什么需要它？
答:多了 review 环节和讨论记录——代码合入前有人过目；这是团队的质量闸，也是责任追溯链

(5)merge 和 rebase 的区别一句话？
答:merge 保留真实历史（多一条合并 commit），rebase 改写历史换一条干净的直线——公共分支禁止 rebase
